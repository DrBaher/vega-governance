## 1. Problem Statement

Agent wikis grow. At 10 entries, linear scanning works — the agent reads everything and finds what it needs. At 50+ entries across process_rules, reasoning_corrections, and role-specific pages, linear scanning wastes context budget on irrelevant entries and risks missing relevant ones buried in volume.

CORTEX is a navigation layer over the wiki. It doesn't change the wiki structure. It adds a way to find the right knowledge for the current task without reading everything.

---

## 2. Architecture Overview

CORTEX has two execution layers:

**Script layer** (runs in the VEGA Orchestrator, outside agent sessions):
- Computes strengths, heat scores, evidence counts, decay
- Reads agent log.md and orchestrator execution logs for consultation data
- Generates agent-facing `concepts.md` (ranked lists)
- Generates `concept_graph.md` for UNIVERSAL (cross-agent)
- All arithmetic, all maintenance, all bookkeeping

**Agent layer** (runs inside agent API calls, in-context):
- Reads concepts.md at session start (ranked lists — no numbers, no formulas)
- Decomposes tasks into concepts (functional + structural)
- Follows ranked lists to find relevant wiki entries
- Logs what was consulted (via LOG_ENTRY, verified by orchestrator)
- Zero arithmetic, zero maintenance, zero bookkeeping

The agent never sees strengths, heat scores, evidence counts, or decay factors. It sees ranked lists. The richness of the CORTEX model is invisible to the agent and handled entirely by the orchestrator's script pipeline.

## 4. Core Model

> **Execution context:** Structural design. Read by: spec maintainer, script implementer.

Two types of nodes. One type of link.

**Wiki entries** — individual rules, corrections, and knowledge items. These exist in the wiki already. Each has an ID (PR-01, RC-03, etc.).

**Concepts** — functional or structural tags that describe what a wiki entry is about. Concepts are the navigation vocabulary.

**Links** — a many-to-many weighted connection between a wiki entry and a concept. Each link carries:

```
entry_id: PR-03
concept: verification
type: functional
strength: 3.2     (composite weight — script-computed)
evidence: 5        (tasks where this entry was consulted for this concept)
last_consulted: 2026-05-20
```

A wiki entry can link to many concepts. A concept can link to many wiki entries.

---

## 5. Concept Types

> **Execution context:** Agent (task decomposition) + Script (type multiplier in heat calculation).

Concepts are unconstrained — anything can be a concept. But concepts are typed, and the type affects navigation weight:

| Type | Description | Weight multiplier | Examples |
|------|-------------|-------------------|----------|
| **Functional** | What the agent is trying to accomplish | 1.5× | verification, propagation, disambiguation, triage, escalation, comparison, completeness, accuracy |
| **Structural** | What objects, entities, or artifacts are involved | 1.0× | SCN, DOC, test-model, L0, build-report, scope-document |
| **Domain** | Domain-specific knowledge areas | 1.0× | (project-specific) |

**Constraint:** When decomposing a task into concepts, at least one must be functional. This forces the agent to think about what it's trying to accomplish, not just what objects are involved.

**Why functional concepts weight higher:** They widen discovery. "SCN" finds SCN-specific entries only. "Verification" finds verification lessons regardless of which document type they came from — including lessons learned in a completely different context that apply to the current task. Functional concepts prevent the agent from only finding what it already knows to look for.

## 6. Strength Formula

> **Execution context:** Orchestrator script (`cortex_script.py`). Agent never sees these numbers.

```
strength = importance × validation × (1 + log(evidence + 1)) × recency_factor
```

| Factor | Source | Values | Updateable? |
|--------|--------|--------|-------------|
| **Importance** | Set at entry creation, updated during wiki maintenance | P0=1.0, P1=0.7, P2=0.4, P3=0.2 (these are entry importance, not SG↔OP priority) | Yes — promoted/demoted when evidence shows different importance |
| **Validation** | Updated on evidence accumulation or corrections | confirmed=1.0, reinforced=0.8, tentative=0.5, superseded=0.1 | Yes |
| **Evidence** | Counted from orchestrator execution logs (consultation tracking) | Integer, grows from 0 | Automatic — script counts |
| **Recency** | Computed from last consultation date | See §12 decay table | Automatic — script computes |

**Recomputation triggers:** After every agent execution (CORTEX script runs in orchestrator post-execution pipeline).

## 7. Heat Spot Calculation

> **Execution context:** Orchestrator script. Output: ranked lists in concepts.md, consumed by agent.

When generating concepts.md, the script pre-computes heat scores for each entry under each concept:

```
heat_score(entry, concept) = concept_type_multiplier × link_strength
```

For task-time heat (computed by script when task concepts are known, or approximated via pre-ranked lists):

```
task_heat(entry) = sum over task_concepts of (overlap × type_multiplier × link_strength)
```

Where overlap = 1 if the task concept matches an entry concept, 0 otherwise.

**In practice:** The script generates ranked lists per concept in concepts.md. The agent reads the lists for its task's concepts and follows them. The per-concept ranking is the pre-computed heat. Cross-concept aggregation (an entry appearing in multiple task-concept lists) is visible to the agent naturally — PR-03 appearing in both the "verification" and "SCN" lists is a stronger signal than appearing in only one.

## 8. Navigation Modes

> **Execution context:** Agent (selects mode based on task type). Script provides ranked lists that all modes read from.

### 8.1 Mode Selection by Task Type

| Task type | Default mode | Examples |
|-----------|-------------|---------|
| **Producing formal artifacts** (SCN, TCN, validation, triage, propagation) | Completeness | SG producing SCN, TG triaging TFR, SG validating DOC |
| **Answering questions, routine lookups** | Search | BR answering build question, processing routine DEV |
| **Building understanding, compiling new rules** | Definition | Any agent writing new process_rules entries |
| **Classifying, diagnosing** | Classification | TG triage (build vs test vs scope defect) |

### 8.2 Mode Behaviors

| Mode | Budget | Strategy | Stop condition |
|------|--------|----------|---------------|
| **Search** | N entries (task-type based) | Follow top-ranked entries from matching concept lists | First satisfactory result or budget exhausted |
| **Completeness** | All entries above overlap threshold (≥2 shared concepts) + all high-importance entries regardless of overlap | Full sweep within thresholds | No early stop — all qualifying entries read |
| **Definition** | Introspective — compare across entries | Given entries tagged with a concept: which co-occurring concepts appear in EVERY entry (essential) vs some (incidental)? | Understanding achieved — essential vs incidental concepts identified |
| **Classification** | All candidate definitions compared | Collect characteristics for each possible category, compare subject against each, score overlap | Best match identified with confidence |

### 8.3 Mode Composition

Real tasks often span modes. The default mode sets the starting strategy and budget, but the agent can extend into adjacent modes during execution:

- A triage task starts as **Classification** (what type of defect?) but may need **Completeness** (don't miss the mock-detection rule) and **Search** (find similar past triages).
- An SCN production task starts as **Completeness** but may need **Definition** (what exactly counts as a cascade?) mid-task.

The agent signals mode extension in its LOG_ENTRY: "Started as Classification, extended to Completeness after initial triage was ambiguous." The script uses this to improve future concept rankings for similar task types.

## 9. Task Decomposition Protocol

> **Execution context:** Agent (in-context reasoning).

When the agent receives a task:

1. **Identify task type.** Match against the mode table (§8.1).
2. **Decompose into concepts.** Extract functional and structural concepts from the task. Minimum one functional concept required.
3. **Check wiki size.** Below ~15 entries → linear scan (CORTEX not needed). Above → concept navigation.
4. **Read matching concept lists from concepts.md.** Find concepts matching the task, read top-ranked entries.
5. **Execute the task** using retrieved knowledge.
6. **Log consultation** in LOG_ENTRY: which concepts were used, which entries were consulted, mode used, any mode extensions.

**Decomposition example:**

Task: "Validate DOC-SE-003 against SCN-SG-002"

Concepts:
- `validation` (functional — primary goal)
- `SCN-application` (functional — what's being validated)
- `propagation` (functional — checking cascade effects)
- `DOC` (structural)
- `SCN` (structural)

Mode: Completeness (producing formal validation artifact).

## 10. Retroactive Concept Assignment

> **Execution context:** Orchestrator script (`cortex_script.py`), reading orchestrator execution logs and agent LOG_ENTRY.

After each agent execution, the CORTEX script processes two data sources:

**Source 1 — Orchestrator consultation record (primary, reliable):**
The orchestrator tracked which wiki entries were included in the API call. This is observable fact, not self-reported. The script increments evidence counts for each (entry, concept) pair where:
- The entry was included in the API call
- The task's concepts (from agent's LOG_ENTRY) match any of the entry's existing concepts

**Source 2 — Agent usefulness signal (secondary, optional weight modifier):**
If the agent's LOG_ENTRY flags specific entries as "directly relevant" vs "background," the script applies a weight modifier:
- "directly relevant" → evidence increment × 1.5
- "background" or unmentioned → evidence increment × 1.0
- Not self-reported → default × 1.0

Source 1 alone is sufficient. Source 2 refines when available. The script never depends on Source 2 for correctness.

**New concept links:** If the orchestrator log shows an entry was consulted during a task with concepts the entry doesn't yet have, the script creates new links with evidence=1, validation=tentative. This is how the concept graph grows — not from speculation at creation, but from real usage patterns.

**Concept assignment at entry creation — two cases:**

*Agent-created entries (normal operation):* When an agent creates a new wiki entry (process rule, reasoning correction) during task execution, the script inherits the task's concepts automatically from the LOG_ENTRY. No speculative tagging — concepts come from the real task context that produced the entry. Assigned with evidence=1, validation=tentative.

*Seeded entries (initialization):* Wiki seeds loaded at project start have no usage history — no task context to derive concepts from. Once the wiki exceeds the scan threshold, untagged entries become invisible to concept navigation: no concepts → not in ranked lists → never consulted → never earn concepts. These need initial speculative tags: 2-3 obvious concepts assigned during seed preparation or by the script on first activation, with evidence=0, validation=tentative. Usage-based concepts accumulate and eventually dominate.

## 11. Failure-Triggered Reload

> **Execution context:** Agent (decides to extend budget) + Script (adjusts evidence on reload discovery).

When a task outcome is unsatisfactory (REV received, finding rejected, triage overridden):

1. The agent extends its exploration — follows the next tier of entries in concept lists that the original budget cut off.
2. If a previously unvisited entry proves useful during reload, the agent flags it in LOG_ENTRY.
3. The script applies a 3× evidence multiplier for reload discoveries. A single "this saved me after a failure" event matters more than 5 routine consultations.
4. If reload also fails, the agent requests OP guidance (human breaks the loop).

**This prevents fossilization.** Without reload, high-ranked entries reinforce and low-ranked entries atrophy. The wiki becomes a filter bubble. Reload is the mechanism that discovers valuable low-ranked entries and promotes them.

## 12. Decay

> **Execution context:** Orchestrator script (periodic computation).

Links not consulted over N sessions slowly decay via recency_factor:

| Sessions since last consultation | Recency factor |
|----------------------------------|----------------|
| 0-5 | 1.0 |
| 6-10 | 0.85 |
| 11-15 | 0.7 |
| 16-20 | 0.55 |
| 20+ | 0.5 (floor) |

The floor at 0.5 ensures old knowledge never fully disappears. A rule from session 1 that hasn't been consulted in 30 sessions is still findable — just deprioritized. If reload discovers it, the recency resets to 1.0.

## 13. Agent-Facing Format (concepts.md)

> **Execution context:** Written by orchestrator script. Read by agent.

The agent never sees strengths, evidence counts, or decay factors. concepts.md contains ranked lists only:

```markdown
# Concept Navigation — [Agent Code]

Last generated: [date] by orchestrator

## verification (functional)
Ranked entries: PR-03, U1, U2, PR-07, RC-08

## propagation (functional)
Ranked entries: PR-07, U10, RC-08, PR-03

## SCN (structural)
Ranked entries: PR-03, PR-10, RC-01

## triage (functional)
Ranked entries: PR-15, U6, U9, RC-05, PR-02

## Entry Profile Summary (ranked by strength)
PR-03: [verification, completeness, SCN, propagation]
PR-07: [propagation, cross-reference, version-bump]
U1: [verification, accuracy]
RC-08: [propagation, verification, surface-check]
```

The Entry Profile Summary gives the agent a reverse lookup: "I'm reading PR-03 — what concepts is it relevant to?" Concepts are listed in descending strength order so primary associations come first. This helps the agent identify unexpected connections during task execution.

**Script-internal data** (not in concepts.md, stored separately by the orchestrator):

```json
{
  "links": [
    {"entry": "PR-03", "concept": "verification", "type": "functional",

  ],
```

2. Detects concepts appearing in 3+ agents → candidate for UNIVERSAL
3. Detects alias patterns → normalizes canonical name

## 15. Concept Proliferation

> **Execution context:** Orchestrator script (monitoring) + Agent (tagging discipline).

**Proliferation is an advantage for search, a risk for completeness.**

No hard limit on concepts per entry. Soft guideline: 3-7 concepts per entry is healthy. Monitoring thresholds:

| Condition | Signal | Action |
|-----------|--------|--------|
| Entry with >10 concepts | Entry may be too broad | Script flags for agent review during self-lint |
| Concept with only 1 connected entry | Potential orphan | Script flags — merge with broader concept? |
| Two concepts with >80% overlap in connected entries | Potential synonyms | Script flags for normalization |

## 16. Self-Lint for Concepts

> **Execution context:** Agent (during self-lint per D-ARCH-022) + Script (provides lint report).

Added to the agent self-lint protocol (framework §6):

| Check | Performed by | Action |
|-------|-------------|--------|
| Orphan concepts (0-1 entries) | Script generates report | Agent reviews during lint: merge or flag |
| Overloaded entries (>10 concepts) | Script generates report | Agent reviews: split entry or merge concepts |
| Synonym detection (>80% overlap) | Script generates report | Agent decides canonical name, script merges |
| Dead links (entry deleted from wiki) | Script detects automatically | Script removes link, recomputes |
| Stale concepts (not consulted 20+ sessions) | Script detects via decay | Flagged in lint report — still relevant or prune? |
| Missing functional (task logged without functional concept) | Script detects from LOG_ENTRY | Flagged — review task decomposition quality |

The script generates a lint report. The agent reviews during scheduled self-lint (every 10 sessions per D-ARCH-022). The agent makes judgment calls (merge vs keep). The script applies the mechanical changes.

## 18. Initialization

> **Execution context:** Orchestrator (initialization sequence).

### 18.1 General framework (new project, CORTEX active from start)

- All agents start with empty concepts.md
- Wikis grow through normal operation
- Once an agent's wiki exceeds ~15 entries (the CORTEX_SCAN_THRESHOLD), concepts.md begins providing value
- Below threshold, agents use linear scan as before
- No bootstrap work required — concepts accumulate from usage automatically

### 18.2 Existing project (e.g., LOINC, activating CORTEX mid-project)

Option A — Cold start: activate CORTEX, start with empty concepts.md, let it grow from new consultations. Some initial runs will underperform (sparse graph) but the wiki content is still there and accessible via linear scan below threshold. No migration work.

Option B — Warm start: the orchestrator script makes a one-time pass through existing log.md files (if they exist) and retroactively builds initial concepts.md from historical consultation patterns. This is a script operation, zero agent cost.

Recommendation: Option B if log.md files have meaningful history. Option A otherwise.

## 19. Open Questions

1. **Concept vocabulary convergence.** With 9 agents tagging freely, how long until the vocabulary stabilizes? SYS normalizes at the UNIVERSAL level, but agent-local synonyms will exist during the convergence window. Is this acceptable, or does it need faster normalization?

2. **Mode composition learning.** When agents extend modes mid-task, should the script learn task-type → mode-combination patterns and pre-suggest composite modes for future similar tasks? Adds complexity but could reduce agent reasoning overhead.

3. **Cross-agent concept navigation.** If an agent finds a concept in UNIVERSAL/concept_graph.md that links to knowledge in another agent's wiki, it can't access that knowledge directly. Current answer: SYS extracts generalized summaries into UNIVERSAL. Is that sufficient, or does the orchestrator need a mechanism for cross-agent knowledge retrieval?

4. **Optimal CORTEX_SCAN_THRESHOLD.** Set at 15 entries based on context window estimates. Should be validated empirically — actual performance comparison of linear scan vs concept navigation at different wiki sizes.

5. **Consultation-only vs consultation + usefulness.** Current design uses both (Source 1 primary, Source 2 modifier). Should be validated empirically — does Source 2 actually improve ranking quality, or does it add noise?

## Appendix A: cortex_script.py Interface

> **Execution context:** Script implementer reference.

```python
class CortexScript:
    def __init__(self, config):
        self.scan_threshold = config.CORTEX_SCAN_THRESHOLD
        self.data_dir = config.STATE_DIR + "/cortex"

    def post_execution(self, agent_code, log_entries, consultation_record, wiki_updates):
        """Called by orchestrator after each agent execution."""
        # 1. Extract task concepts from log_entries
        task_concepts = self._extract_task_concepts(log_entries)

        # 2. Update evidence from consultation_record (Source 1)
        self._update_evidence_from_consultation(
            agent_code, consultation_record, task_concepts
        )

        # 3. Apply usefulness modifiers from log_entries (Source 2)
        self._apply_usefulness_modifiers(agent_code, log_entries)

        # 3b. Auto-tag newly-created wiki entries with task concepts
        # When wiki_updates contain a new entry (PR-22 didn't exist before),
        # tag it with the current task's concepts at evidence=1, validation=tentative.
        # No speculation — concepts come from the actual task that created the entry.
        self._tag_new_entries(agent_code, wiki_updates, task_concepts)

        # 4. Create new links for entries consulted under new concepts
        self._create_new_links(agent_code, consultation_record, task_concepts)

        # 5. Handle reload discoveries (3x evidence multiplier)
        self._process_reload_discoveries(agent_code, log_entries)

        # 6. Recompute all strengths for this agent
        self._recompute_strengths(agent_code)

        # 7. Regenerate concepts.md (ranked lists)
        self._generate_concepts_md(agent_code)

    def periodic_maintenance(self, agent_code):
        """Called periodically (e.g., every 10 executions)."""
        # 1. Apply decay to all links
        self._apply_decay(agent_code)

        # 2. Generate lint report
        lint_report = self._generate_lint_report(agent_code)

        # 3. Regenerate concepts.md
        self._generate_concepts_md(agent_code)

        return lint_report

    def sys_cross_agent(self):
        """Called during SYS execution."""
        # 1. Read all agents' concept data
        all_concepts = self._read_all_agent_concepts()

        # 2. Detect cross-agent patterns (concepts in 3+ agents)
        cross_patterns = self._detect_cross_patterns(all_concepts)

        # 3. Detect aliases (>80% overlap)
        aliases = self._detect_aliases(all_concepts)

        # 4. Generate UNIVERSAL/concept_graph.md
        self._generate_concept_graph(cross_patterns, aliases)

        return cross_patterns, aliases
```

## Appendix B: Two-Phase Approach

> **Execution context:** Orchestrator configuration (automatic per-agent transition).

The concept graph is not always needed. The transition is controlled by the orchestrator:

**Phase 1 — Linear scan (small wiki).** When an agent's wiki has fewer entries than CORTEX_SCAN_THRESHOLD (~15), the orchestrator does not include the CORTEX navigation block in the system prompt and does not generate concepts.md for that agent. The agent scans linearly, unaware of CORTEX. This catches unexpected connections — a rule not yet tagged might contain a relevant insight.

**Phase 2 — Concept navigation (large wiki).** When an agent's wiki entry count crosses the threshold, the orchestrator activates CORTEX for that agent: generates concepts.md, includes the CORTEX navigation block in the system prompt. Transition is automatic and per-agent — SG might be in Phase 2 while TE is still in Phase 1.

The orchestrator tracks wiki entry counts per agent after each execution. Transition is one-way: once activated, CORTEX stays active for that agent even if entries are later pruned below threshold (the graph is already valuable by then).
